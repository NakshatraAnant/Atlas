# Decision log

Short ADRs. Earlier decisions (ADR-001..011) were made in sessions 1–2 and are summarised where known; the full text was never committed.

| ID | Date | Decision | Why | Reversible? |
|---|---|---|---|---|
| ADR-008 | 18 Oct 2026 | TypeScript end to end; PGlite (PostgreSQL in WASM) for local dev and tests; node-postgres against managed PostgreSQL in production. | No Python/WSL/Docker on the dev machine. One language keeps the calculation engine testable everywhere. | Yes |
| ADR-012 | 19 Oct 2026 | **Supabase = hosted PostgreSQL; the ATLAS API is the only client.** Tables live in non-public schemas (not exposed by Supabase REST). RLS is enabled on every table with *no* permissive policy, and `anon`/`authenticated` lose all privileges (migration 004). The API connects as the table owner and enforces authorisation itself (tested: user-isolation suite). | The existing server already has tested auth, isolation and audit. Exposing tables to browser-side Supabase clients would duplicate every authorisation rule as RLS policies with two sources of truth. Deny-by-default RLS still protects against a leaked anon key or accidental schema exposure. | Yes: per-table policies can be added later if a browser-direct path is ever wanted. |
| ADR-013 | 19 Oct 2026 | **Keep the existing authentication (scrypt password hashing, server sessions, TOTP, lockout) instead of switching to Supabase Auth for now.** | It is implemented and covered by tests (ACC-01..08). Migrating identities to Supabase Auth would mean rewriting sessions, MFA, admin 2-step and account deletion, with no user-visible gain for a local, pre-launch product. Supabase Auth remains an option before launch (would move `app.users` identity to `auth.users` with a profile table). | Yes, with a migration plan |
| ADR-014 | 19 Oct 2026 | Region `ap-south-1` (Mumbai) for the Supabase project. | Users are in India; lowest latency; keeps data in India, which simplifies DPDP-related data-residency questions (legal review still required). | New project needed to change |
| ADR-015 | 19 Oct 2026 | Supabase migrations are applied from the same version-controlled files and recorded in `ops.schema_migrations` with identical checksums; parity is proved by `apps/api/src/db/fingerprint.sql`. | One migration history for local and hosted. No dashboard-only changes. | — |
| ADR-016 | 19 Oct 2026 | `DATABASE_SSL` (`require` for dev, `verify-full` + CA in production; enforced by `assertProductionSafe`). | Supabase connections cross the internet; production must verify the server certificate. | Yes |
| ADR-017 | 19 Oct 2026 | Default synthetic universe 40 companies (was 120), one default for seed and API. | The 120-company seed crashes PGlite in the calculation stage (WASM "memory access out of bounds"); the session-2 seed log stops at the same step, so the full seed has likely never completed. 40 seeds in 155 s. A mismatched size between seed and API would make daily cycles ingest unknown companies. | Yes: raise once the calculation stage is made memory-bounded. |
| ADR-018 | 19 Oct 2026 (session 4) | **Root fix for the embedded-engine crash; ADR-017 superseded.** Point-in-time fundamentals are loaded in bounded company batches (`ATLAS_PIT_BATCH_COMPANIES`, default 10) and both calculation stages process one batch at a time. Seeds above 150 companies build directly in the on-disk store (`ATLAS_SEED_MODE=auto|memory|disk`). The synthetic universe size is read from the seeded database; the default for a new seed is back to 120. | Diagnosis (pipeline trace): one unbounded `loadPit` query (~450k rows at 120 companies) overflowed PGlite's protocol buffer → "unreachable"/"memory access out of bounds" at only ~620 MB WASM memory. Separately, the in-memory seed needs ~3× the database size and hit the 4 GB WASM ceiling at 500 companies. Batching changes no value (hash-identical to the old code); disk and memory seeds are hash-identical. | Yes |
| ADR-019 | 19 Oct 2026 (session 4) | **A missing value is never a number in the evidence trail.** Claims for metrics that are not reported, not available or not meaningful carry `value: null` (stored with `check_result='not_numeric'`), and the claim checker never matches text against them. | The evaluation found 17 answers whose evidence recorded `0` for a not-meaningful metric (e.g. debt to equity for a financial-sector company). A model-written narrative saying "0" would have passed the checker against fabricated evidence. | Yes |
| ADR-020 | 19 Oct 2026 (session 4) | **Assistant policy: any question about future price direction is advice/prediction, whatever the company name; a company name not in the catalogue is reported as not covered instead of being silently ignored or fuzzily matched.** Fuzzy matching is used only when exactly one covered company scores ≥ 0.7. | Red-team cases such as "Will Kaveri Foods go up next month?" and "What is the ROCE of Tata Motors?" were answered as research. | Yes |
| ADR-021 | 19 Oct 2026 (session 4) | e2e tests run on the installed Microsoft Edge through Playwright's `msedge` channel; real-PostgreSQL tests run on `embedded-postgres` (PostgreSQL 17 binaries from npm) instead of Docker. | No WSL/Docker, and downloading browser binaries is avoided. Both run locally and offline after `npm install`. | Yes |
